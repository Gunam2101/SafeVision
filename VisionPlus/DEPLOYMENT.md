# Deployment Guide

## 1. Vercel (frontend) + Render (backend) — recommended for this project

This is the deployment path this repo is configured for (`render.yaml` +
`frontend/vercel.json`).

### 1a. Backend on Render

1. Push this repo to GitHub/GitLab.
2. In the Render dashboard: **New → Blueprint**, point it at the repo.
   Render reads `render.yaml` at the repo root automatically and creates:
   - A managed Postgres instance (`visionplus-db`)
   - A Docker-based web service (`visionplus-backend`) built from
     `backend/Dockerfile`, wired to `DATABASE_URL` from that Postgres
     instance automatically, with `SECRET_KEY` auto-generated (never the
     code default).
3. After the first deploy, set these in the Render dashboard (they are
   intentionally **not** hardcoded anywhere in the repo):
   - `CORS_ALLOWED_ORIGINS` → your Vercel URL(s), e.g.
     `https://visionplus.vercel.app`
   - `GROK_API_KEY` (optional) → enables the real LLM chatbot instead of
     the built-in rule-based one
4. Verify: `https://<your-service>.onrender.com/system/health` → `200`.

**Known limitation, documented not hidden:** Render's free-tier disk is
ephemeral — uploaded videos and generated reports do **not** survive a
redeploy on the free plan. For real production use, attach a paid
persistent disk (Render Dashboard → Disks) mounted at `/app/uploads` and
`/app/reports`, or move media storage to S3/object storage (not
implemented in this repo — see PROJECT_AUDIT.md).

**Also:** `GET /stream/` (live monitoring) opens the *server's local
webcam* (`cv2.VideoCapture(0)`). A Render web service has no camera
hardware, so in production this will correctly show "No camera available"
— that's expected behavior, not a bug. Point `camera_index` at an RTSP
source, or extend the stream endpoint to open an RTSP URL instead of a
local device index, to use a real camera in production (scaffolded, not
implemented — see PROJECT_AUDIT.md).

### 1b. Frontend on Vercel

1. In the Vercel dashboard: **New Project**, import the repo, set the
   **Root Directory** to `frontend/`. Vercel auto-detects Vite via
   `frontend/vercel.json`.
2. Set these Vercel **Project Environment Variables** (Settings →
   Environment Variables) before building — Vite bakes `VITE_*` vars in at
   *build* time, so they must be set here, not just in a local `.env`:
   - `VITE_API_BASE_URL` → your Render backend URL, e.g.
     `https://visionplus-backend.onrender.com`
   - `VITE_DEV_MODE` → `false` for a real deployment (set `true` only for a
     temporary, login-free public demo — see the Dev Mode warning below)
3. Deploy. Vercel serves the built SPA with client-side routing handled by
   the rewrite rule in `frontend/vercel.json`.

**Do not set `DEV_MODE=true` / `VITE_DEV_MODE=true` on a real deployment.**
Dev Mode bypasses authentication entirely — every request is treated as an
administrator with no credentials. It exists for local development and
temporary demos only.

## 2. Docker Compose (single host, self-managed)

```bash
cp .env.example .env
# Edit .env: set a real SECRET_KEY and POSTGRES_PASSWORD
docker compose up --build -d
```

Services:
- `db` — Postgres 16, persisted in the `pgdata` volume, healthchecked before
  `backend` starts.
- `backend` — runs `alembic upgrade head` then `uvicorn` on `:8000`.
  Uploads/reports/model weights persist in named volumes so they survive
  container rebuilds.
- `frontend` — built with Vite, served by nginx on `:80` (mapped to host
  `:3000`). `VITE_API_BASE_URL` is baked in at build time via the
  `VITE_API_BASE_URL` build arg in `docker-compose.yml` — change it there if
  the API is reachable at a different host from the browser's perspective.

Put a reverse proxy (Caddy/Traefik/nginx) with TLS in front of ports 3000
and 8000 for a real deployment; this compose file is intentionally plain
HTTP for local/staging use.

## 3. Environment variables that matter in production

| Variable | Where | Why |
|---|---|---|
| `SECRET_KEY` | backend | JWT signing key — must be long/random, never the default. Auto-generated by Render's Blueprint; must be set manually for Docker/self-hosted. |
| `DATABASE_URL` | backend | Point at your Postgres instance. `postgres://` and `postgresql://` schemes both work — normalized automatically (see `app/db/database.py`). |
| `DEV_MODE` | backend | Must be `false` in any real deployment — see warning above. |
| `CORS_ALLOWED_ORIGINS` | backend | Must include your real frontend origin(s); never left as a wildcard in production. |
| `GROK_API_KEY` | backend | Optional — enables real LLM chatbot responses. |
| `VITE_API_BASE_URL` | frontend (build-time) | Where the browser reaches the API. |
| `VITE_DEV_MODE` | frontend (build-time) | Must be `false` in any real deployment. |

## 4. Database migrations

This project ships both `Base.metadata.create_all()` (auto-create, used by
default/dev) and real Alembic migrations (`backend/alembic/`). In
production, prefer migrations so schema changes are tracked and
reversible:

```bash
cd backend
alembic upgrade head          # apply
alembic revision --autogenerate -m "describe change"   # after editing models
```

Render's Blueprint `startCommand`/Docker `CMD` runs `alembic upgrade head`
automatically on every deploy before starting uvicorn.

## 5. Scaling notes (not implemented, for when you need them)

- Video analysis (`POST /analyze/{video_id}`) runs synchronously in-request
  today. For real production video volume, move it to a background worker
  (Celery + Redis, or FastAPI `BackgroundTasks` for light loads) so uploads
  don't block on YOLO inference time.
- `GET /stream/` currently opens the server's local webcam per-request —
  it isn't multi-camera or RTSP-aware yet. A real deployment would need a
  stream-per-camera-id design, likely with a media server (e.g. MediaMTX)
  in front of RTSP/ONVIF sources rather than piping raw frames through
  FastAPI directly.
- Static file serving (`/media/uploads`, `/media/reports`) is fine for
  moderate volume; move to S3/object storage + signed URLs if upload
  volume grows.
- The live-monitoring start/stop state (`app/services/live_state.py`) is an
  in-process singleton — correct for Vision+'s current single-process
  deployment shape, but would need to move to a shared store (Redis) if the
  backend is ever scaled to multiple workers/dynos, since each worker would
  otherwise have independent start/stop state.

## 6. Health checks

- Backend: `GET /system/health`
- Frontend: `GET /` (nginx serves `index.html` in Docker; Vercel serves the
  static build directly)

Both are wired into the Dockerfiles' `HEALTHCHECK` directives and Render's
`healthCheckPath`.
